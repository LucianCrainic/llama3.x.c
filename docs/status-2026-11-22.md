# Status of 22 November 2026: what was done, the results, and what is left

This file summarises the work of 21–22 November 2026. Every number is from the linked result documents. Each of those has a validation record with the job ids and checks.

The cluster went into a scheduled maintenance drain on 22 November, expected to last 3 days. The work below was wrapped up without waiting for it; the single job it blocked is listed in §6.

Labels follow the result documents:
- **1S / 2S**: one or two sockets.
- **P**: a 2048-token prompt. **L**: the long prompt. **D**: decode (86-token prompt, 128 generated).
- **TTFT**: time to first token.

All runs are Llama 3.1 8B Instruct, W8A8, single request, on Xeon Max 9480 nodes.

## 1. Cross-engine comparison (llama3.x.c, llama.cpp, vLLM CPU)

Results: [xengine-results.md](xengine-results.md). Validation: [xengine-results-validation.md](xengine-results-validation.md). Plan: [plans/xengine-comparison.md](plans/xengine-comparison.md).

Every cell passed its checks, and an independent re-derivation confirmed all 18 headline cells (maximum deviation 0.17%).

Decode tok/s / TTFT for P, before the prefill work (median of 3):

| Engine | Sockets | Flat HBM | Flat DDR | Cache mode |
| --- | --- | --- | --- | --- |
| llama3.x.c | 1S | 51.9 / 2.26 s | 29.8 / 2.53 s | 46.3 / 2.52 s |
| llama3.x.c | 2S | 99.1 / 1.37 s | 55.9 / 1.49 s | 79.2 / 1.59 s |
| llama.cpp | 1S | 40.6 / 4.56 s | 24.9 / 4.60 s | 32.8 / 4.63 s |
| llama.cpp | 2S | 23.9 / 3.81 s | 29.7 / 3.19 s | 19.3 / 5.71 s |
| vLLM (HBM patched) | 1S | 40.5 / 0.62 s | 24.9 / 0.74 s | 34.1 / 0.67 s |
| vLLM (HBM patched) | 2S | 61.2 / 0.37 s | 41.2 / 0.46 s | 50.2 / 0.40 s |

Findings:
- **HBM helps decode, not prefill.** Decode on HBM is 1.63–1.74x DDR for all three engines; prefill gains only 1.00–1.20x, because it is compute-bound.
- **llama3.x.c decodes fastest everywhere** and scales 1.91x to two sockets.
- **llama.cpp gets slower on two sockets on HBM** (0.59x): 4.4 GB per token crosses UPI.
- **Stock vLLM never reaches HBM.** It rebinds memory to its cores' DDR node and ignores `numactl`. The HBM row needs a small worker patch.
- **Cache mode** recovers 75% (1S) and 54% (2S) of the HBM decode gain for llama3.x.c.

Side corrections, both merged:
- **HBM CAS counts are 32 B, not 64 B** (calibrated). Counter-derived HBM byte and bandwidth figures in 10 earlier documents were halved and marked.
- **The stock-vLLM note** is in the headline notes.

### 2.2 What changed

Saving in TTFT at P 1S, measured (modelled):

| Change | Results | Saving |
| --- | --- | --- |
| Parallel K/V store with page pre-fault, embedding/RoPE on the team, balanced 2D GEMM partition | bitwise | −0.32 s (−0.31) |
| Pipelined AMX-INT8 Q8_0 kernel | bitwise | −0.19 s (−0.55) |
| Fused RMSNorm and quantizer | bitwise | −0.07 s (−0.09) |
| Vector `exp` in SwiGLU | gated | −0.07 s (−0.10) |
| AMX-BF16 flash attention with a persistent BF16 K/V copy | gated | −0.33 s (−0.35) |
| K-blocking plus M = 1024 rows per microbatch | bitwise | −0.15 s (−0.05) |
| Per-channel weight format | opt-in | −0.39 s (−0.3) |

Notes:
- **Fixes not marked bitwise** were made default only after the Hugging Face gate passed on the batched prefill path.
- **The pipelined kernel fell short of its model** because the prototype ran on cache-resident operands.
- **M = 1024** cut HBM reads per prefill from 65.7 to 28.6 GB (1S).
- **The per-channel format** is a new file version, written by the extended converter (`export.py`); it also imports the RedHatAI W8A8 checkpoint (`--hf-w8a8`). The model file selects it.

### 2.3 Accuracy

Hugging Face gate: rms ≤ 0.2, max ≤ 16, argmax ≥ 0.9.

| Configuration | rms |
| --- | --- |
| Before, batched prefill path | 0.110–0.133 |
| New defaults, batched prefill path | 0.116–0.138, argmax 1.0 (pass) |
| Per-channel format, our RTN export | 0.34–0.40 (fail) |
| Per-channel format, imported RedHatAI checkpoint | 0.33–0.40 (fail) |
| vLLM's own scheme, modelled with fake-quant on the HF model | 0.395 (fail) |
| vLLM's weights with FP32 activations | 0.146 (pass) |

The cause of the failures is per-token activation quantization. So vLLM's prefill lead is measured at lower logit fidelity, and a dated note says so in [xengine-results.md](xengine-results.md). At equal fidelity (per-channel) llama3.x.c is 1.47x off vLLM at P 1S. At the gate (gs64) it is 2.1x off, with about 3x lower rms.

### 2.4 Found and fixed on the way

- **The HF gates had measured only the per-token (decode) path.** `compare_engines.py --both-paths` now judges the per-token and batched paths against one reference, and the gate script uses it.
- **The RedHatAI checkpoint contains int8 −128,** which breaks the VNNI weight-negation trick in the decode GEMV. The importer maps −128 to −127 and counts it: 300,231 values, 4.3e-5 of all weights. The prefill AMX path was exact.
- **Two test changes, with their derivations recorded:**
  - A test that compared AMX attention with itself now compares against tiled.
  - The 1S-vs-2S AMX-attention budget is derived by the triangle inequality, with a check that most rows stay sharp.

## 3. Two-socket Wo/W2 reduction interleaved with the projection

Results: [prefill-gap.md](prefill-gap.md) §10. Validation: [prefill-gap-validation.md](prefill-gap-validation.md), deviations 13–16.

### 3.1 Diagnosis

The Wo kernel scales (2.1x on two sockets). Wo's in-situ 23 TOP/s came from the separate add of the partial sums, about 21 ms per prefill, plus waiting for the other socket. A column split of Wo was modelled at only −7 ms and dropped.

### 3.2 Change

`LLAMA_TP_BATCH_REDUCE=interleaved` is the new default. Each worker adds finished blocks between its GEMM compute units. `wo` (Wo only) and `barrier` (the old behaviour) are the ways back.

### 3.3 Results

- **Bitwise** with develop in all three modes, 1S and 2S.
- **P 2S:** −30 ms paired median over 30 interleaved repeats; faster in 19 of 30, and faster in both run modes.
- **L 2S:** −161 to −175 ms (about 4.3%).
- **Decode:** flat.
- **Wo** runs at 38.5 TOP/s, up from 22.2.
- **The add is not hidden** (about 3.5 µs per block on the computing worker). The gain comes from dropping the separate add phase, its dispatch and its barriers.
- **UPI bytes rise** (2.8–3.0 to 3.3–5.0 GB per direction against a 2.15 GB payload). The cause is not yet attributed.

## 4. HBM capacity study (planned, parked)

Plan: [plans/hbm-capacity-study.md](plans/hbm-capacity-study.md).

It covers a 70B model whose weights plus KV cache approach or exceed the 128 GB of HBM:
- weights are 34.4 GiB per socket in Q8_0, and the FP32 KV cache is 320 KiB per token per socket;
- the 56 GiB budget is crossed at about 69k tokens.

Today an over-budget configuration fails at load. It needs engine work before any run: convert, KV tiering, weight tiering, a synthetic KV fill, tests and capture.

The study is parked by the owner's decision of 21 November, which put the focus on prefill.
